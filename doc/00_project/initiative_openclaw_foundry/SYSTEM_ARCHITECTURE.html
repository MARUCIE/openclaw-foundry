OpenClaw Foundry × SOTA Skill Library 架构决策报告

结论先行：Foundry 继续作为唯一产品面与部署控制平面，SOTA 不作为第二运行时或第二公开站点接入，而是收敛为上游 Skill Intelligence Factory，向 Foundry 输出版本化 artifact 与启发式结果。
参与方：Primary Synthesizer、software-simplicity-reviewer、bmad-architect
01

执行摘要

本次不是“把两个项目硬拼成一个仓库”，而是先完成职责去缠绕：产品面、公开入口、部署运行时只保留 Foundry 一套；分类、打分、去重、bundle 候选生成则沉到 SOTA 派生的离线工厂层。
13个平台
统一产品面仍由 Foundry 承接，不拆分平台入口
1个公开站点
不保留第二商城、不保留第二并行推荐站
0个新增关键路径运行时
JIT/MCP 本地运行时不进入公开目录、部署、比武主链路
4个迁移阶段
先冻结 contract，再 shadow run，再 artifact cutover，最后按需启用智能侧车
  • 推荐方案是 artifact-level convergence，不是 repo-level 或 runtime-level fusion。这样既能吸收 SOTA 的高价值能力，又不会把本地状态、遥测、安装器路径污染到 Foundry 的公开产品面。
  • Foundry 的唯一职责被进一步收紧为：发现、比较、部署、管理，以及围绕 13 个平台的一致化控制平面；SOTA 的耐久价值被重定义为：技能工厂、评分规则、taxonomy 映射、bundle 候选生产。
  • 系统的真正切换点是“单一 artifact contract”是否成立，而不是代码是否搬进同一个目录。只要 schema、taxonomy、评分语义、bundle 语义未冻结，就不能宣称完成合并。
  • 回滚策略必须是 artifact 级别：回滚 catalog / bundle 版本即可，不触碰 deploy state、provider 实现与用户机器上的安装态。
02

综合结论

两边确实有“技能目录、分类、推荐、bundle”上的能力重叠，但它们不该以平级产品的方式继续生长；应改成“上游工厂 + 下游产品面”的单向依赖关系。
01

为什么不做整仓硬合并

  • SOTA 带着本地 telemetry、安装器路径、MCP/JIT 运行时假设，这些都不适合进入 Foundry 的公开关键路径。
  • 如果现在强行整合，最终会得到两个事实源、两套路由语义、两套用户入口，产品边界反而更模糊。
  • 用户真正需要的是一个稳定一致的入口，而不是第二个“更聪明但更脆弱”的公开站点。
02

为什么选 artifact 收敛

  • artifact 是最小耦合面：可以承载 catalog、rating、taxonomy、bundle，而不引入额外线上运行时。
  • Foundry 现有 Web、Worker、CLI、Server 都可以消费 artifact，却不必感知 SOTA 的本地实现细节。
  • 这种路径天然支持 shadow run，可对比总量、ID churn、分类分布、评分分布，风险可控。
03

目标边界是什么

  • 公开浏览、筛选、详情、部署、比武、管理等用户链路只出现在 Foundry 名下。
  • Recommendation / route planning 未来可以回来，但必须建立在 Foundry 拥有的 schema 上，并作为可选 sidecar。
  • “是否合并完成”的标准不是 Python 文件是否搬家，而是 Foundry 是否只依赖一套版本化 artifact truth。

管理含义

  • 短期内不做用户可感知的大迁移，先把内部 contract、seed、artifact 管线打通。
  • 所有后续推荐能力都以“Foundry 公开产品稳定性优先”为门槛，不能为了智能度牺牲入口一致性。
03

目标拓扑与职责切分

未来状态不是“双头架构”，而是一个明确的上游到下游链路：Skill Intelligence Factory 产出版本化 artifact，Foundry 统一消费并对外提供发现、部署与运营体验。

Skill Intelligence Factory

  • 负责 ingest、validate、dedup、categorize、score、bundle generation。
  • 可以吸收 SOTA 的启发式、分类规则和 pipeline 资产。
  • 输出必须是版本化 artifact，而不是让下游依赖其本地状态目录。

Discovery Plane

  • 由 Foundry 的 `web/` 与 `worker/` 承接公开浏览、搜索、筛选、详情与目录 API。
  • 它是唯一公开商城与唯一产品面，不再接受第二前台。
  • 任何推荐结果展示都必须挂在 Foundry 自有路由与 schema 下。

Deploy Control Plane

  • 继续由 Foundry 的 CLI、Server、Provider 系统承接。
  • 部署态、用户机器状态、manifest、snapshot 与 provider 实现保持不变。
  • 它不应被 SOTA 的本地 MCP/JIT 运行时反向侵入。

Optional Intelligence Adapter

  • 只在 artifact contract 稳定后才考虑启用。
  • 面向 related skills、route planning、future JIT assembly 等增强能力。
  • 必须是非关键路径 sidecar，可关闭、可回退、不可绑死主站运行。
04

迁移路径与里程碑

迁移顺序必须先收口语义，再验证差异，最后才允许切换生产 artifact；任何先上推荐、后补 schema 的路径都会把未来维护成本放大。
Phase 1 | Contract Freeze
  • 冻结 skill schema、taxonomy 语义、rating 语义、bundle schema。
  • 明确 ID 规范与 dedup 规则。
  • 形成唯一 artifact contract。
Phase 2 | Shadow Run
  • 对比现有 Foundry artifact 与 SOTA 派生产物。
  • 重点看 total count、ID churn、category spread、score distribution。
  • 不改变任何公开入口。
Phase 3 | Artifact Cutover
  • 仅切换 seed/build pipeline 到 canonical artifact。
  • Foundry 的公开 UX、CLI、API 路径保持稳定。
  • 回滚单位为 artifact version。
Phase 4 | Intelligence Opt-In
  • 在 Foundry 自有 schema 上重建 recommendation / route planning。
  • 以 sidecar 形式试点，不进入关键路径。
  • 先验证，再逐步暴露到产品面。

执行纪律

  • 禁止把“未来可能有价值的 SOTA runtime”直接塞进 Foundry 主链路做一次性大合并。
  • 禁止在 contract 未冻结前引入第二公开 UI 或第二 catalog truth。

风险与缓释

最大的风险不是“合并太慢”，而是“边界没拆干净就开始上线新智能能力”，这样会同时制造产品漂移、事实源分裂和回滚困难。

2026-05-18 岗位配置包登录边界

站点入口、Skill/MCP/API 文档复制继续公开；只有岗位配置包的安装命令、文件下载与 pack payload 交付进入注册态动作，避免把普通 Skill 复制也误锁住。

前端边界

  • Skill install modal、Skill detail、MCP 列表、API docs 示例复制全部保持公开。
  • `web/lib/protected-downloads.ts` 服务岗位配置包安装命令复制与单文件下载。
  • `/packs` 的安装/下载动作调用 protected helper，缺少 session 时回跳登录。
  • 安装命令复制只写入 GitHub tag clone 命令，不再签发 Worker download token。
  • 静态 Pages 未配置 `NEXT_PUBLIC_API_URL` 时直接读取 `/data/*.json`，避免 `/api/packs` 404 控制台噪音。

后端边界

  • 邮箱 magic-link 与微信 OAuth 共同作为注册/登录入口。
  • Worker 通过 `POST /api/packs/:id/download-token` 签发短期 token。
  • Worker 通过 `GET /api/packs/:id/file?path=...` 读取 D1/R2 payload 并禁止公共缓存。

发布边界

  • `guide.html` 可继续作为公开说明页发布。
  • install script、manifest、json/zip/config payload 不再作为 public Pages 明文文件发布。
  • CI 先上传 protected payload 到 R2，再 tombstone `web/out/packs` 后部署 Pages。
